# Delta Spec: chat-reader V2（标出消息里文字的来源）

Status: 已批准 2026-11-26　版本：V2
改动对象：`docs/specs/chat-reader.md`（已批准）；`docs/specs/interest-digest.md` 第 1 步（已批准）
依据：`docs/ROADMAP.md` V2「`chat-reader` 区分粘贴内容」；`chat-reader.md` 第 6 节第 2 条；2026-11-26 与作者的讨论和对作者 vault 的只读统计（第 8 节）。

## 1. Objective

V1 把「我」消息里的所有文字都当成我写的。可实际上我常把别的文字贴进去：AI 之前的回答、代码、报错、附件。

V2 把「我」的每条消息切成段，**每段标上来源：这些字是谁写的**。

- 只标来源，**不判断态度**。贴回 AI 的话，可能是「对，就是这个」，可能是「这里不对」，也可能是「在这个基础上改」。我同不同意，要看我自己写的那部分，由以后的 `profile` 结合上下文判断（第 6 节）。
- **不删任何内容**。贴进来的东西说明我关注什么。
- 规则只认**有证据的**来源，对所有用户一样，没有要按人调的门槛。认不出来的就算「我写的」（第 7 节）。

不变的部分：只读，不改任何文件，不调用 AI，不联网；vault 文件格式不变，来源是读取时算出来的。

成功的样子：`eia chats dump --only-me --format jsonl` 里，一段原样贴回的 ChatGPT 回答被标成 `ai`，我在它前后写的话标成 `own`。

## 2. 怎么切段

- 按空行切。
- 代码块（三个反引号包起来的部分）整块算一段，里面有空行也不切开。
- 所有段按原顺序拼回去（段之间补回原来的空行），等于原消息。

## 3. 来源规则（按顺序，先命中的算）

| # | 来源 | 证据 |
|---|---|---|
| R1 | `ai` | 这一段在**同一对话里、这条消息之前**的 AI 回答中原样出现。比较时忽略空白和 Markdown 符号（`*` `_` `` ` `` `#` `>` `|` `-`）。比较前去掉符号后少于 20 个字的段不算，防止「好的」「谢谢」这种短句碰巧一样 |
| R2 | `code` | 代码块 |
| R3 | `error` | 连续 ≥ 2 行符合常见报错格式：Python `Traceback (most recent call last):` / `  File "...", line N`、Java/JS `    at xxx(...)`、`Exception in thread`、Rust `error[E0308]:`、`XxxError:` / `XxxException:` 开头 |
| R4 | `attachment` | 整段都是导入时写的占位：`[附件：...]`、`[文件：...]`、`[文件]`、`[图片：...]`（Claude 把这几种写在同一段里；2026-11-26 实现时补上后三种） |
| — | `own` | 以上都不是 |

- 20 字只用来排除巧合，跟用户是谁无关，不需要校准。
- 我在对话文件里写的笔记（`role: note`）不切段，整条算 `own`。

## 4. Interface

```python
# src/eia/chat/source.py（新文件；reader.py 仍然只做 render.py 的反向）
Source = Literal["own", "ai", "code", "error", "attachment"]

@dataclass(frozen=True)
class Part:
    source: Source
    text: str            # 带着这段后面的空行，所有段直接连起来就是原消息

def split_message(text: str, earlier_ai: str) -> tuple[Part, ...]   # 相邻、来源相同的段合并
def label_chat(chat: ReadChat) -> tuple[tuple[Part, ...] | None, ...]  # 和 chat.messages 一一对应，AI 的消息是 None
def text_of(parts, *, sources) -> str                              # 只拼出指定来源的段
```

## 5. 命令的变化

```
eia chats dump ... [--own-only]     # 只看我的话，且「我」的消息只输出 own 段；全是别的来源的消息不输出
eia chats stats ...                 # 每个平台多一行：各来源的字数
```

- `--only-me` 照旧输出整条消息，不去掉任何内容。
- `--format jsonl`：「我」的消息多一个 `parts` 字段：`[{"source": "ai", "text": "..."}, ...]`（每段去掉首尾空白）；`text` 仍是整条原文，旧的读法不受影响。加了 `--own-only` 时 `text` 只有 own 段，没有 `parts`。
- `--format text`：非 `own` 的段前面加一行 `〔来自 AI〕` / `〔代码〕` / `〔报错〕` / `〔附件〕`，方便自己检查。

## 6. 对使用方的要求

1. **兴趣草稿（`interests draft` 第 1 步，改动 `interest-digest.md`）**：
   - 所有来源的文字都参与归组（贴进来的东西也说明我关注什么）。
   - **每条消息的分量一样，不按字数算**：一条 6 万字的粘贴不能盖过几千条短句。具体做法在实现时定，记进 ADR。
2. **以后的 `profile`（写它的规格时照这条）**：
   - 判断「我认为什么」时，证据必须引用我自己写的 `own` 文字；非 `own` 的段只能当作「我关注 / 处理过什么」。
   - 例：结论「认同某观点」要写成「贴回了这段，并说了『对，就是这样』」，不能只凭贴回就下结论。

## 7. 已知局限

- 从网页、文章复制的文字，如果没有格式，规则认不出来，算 `own`。交给 `profile` 的 AI 看上下文判断。
- 没用代码块包起来的代码，算 `own`（统计里这类不少，但规则一宽就会误伤自己写的文字，见第 8 节）。
- 贴到**另一个**对话里的 AI 回答，R1 认不出来（只比同一对话）。
- 真正准确的办法是在粘贴的那一刻记录下来，官方导出里没有这个信息；以后 `chat-sync`（V2-12）可以考虑。

## 8. 依据：作者 vault 的只读统计（2026-11-26，只算数量，不看内容）

| | ChatGPT | Gemini |
|---|---|---|
| 「我」的消息 | 4,694 条，中位数 22 字 | 4,717 条，中位数 25 字 |
| 含 R1–R4 来源的消息 | 74 条 | 147 条 |
| 这些来源占「我」的总字数 | 约 3.5% | 约 33%（贴回 AI 回答 31%，两个对话就占约 48 万字） |

结论：多数消息是自己写的短句，但少数超长的粘贴按字数占了很大比重，所以第 6 节第 1 条要按条数算分量。

草案第一版试过「疑似粘贴」（长段、像代码、有 Markdown 格式），ChatGPT 有 35% 的字被标成「很长」、19% 被标成「像代码」，多半是作者自己写的；超过 2,000 字的 99 段里也混着作者自己写的见证稿、生活记录。长度不能证明是粘贴，而且门槛因人而异，所以删掉了这一档。
