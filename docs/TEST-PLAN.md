# Test Plan（测试文档）— V0

目的：让"功能还能不能用"随时可查，不依赖任何人的口头保证。
规则来源：test-driven-development（先写测试再写代码）+ docs/CONSTRAINTS.md（测试不许删、不许跳过）。

## 1. 你怎么知道现在是好的

| 方式 | 怎么看 | 什么时候 |
|---|---|---|
| 一条命令 | 在项目目录运行 `python scripts\check.py`（或 `.\check.ps1`），最后一行是 `ALL PASSED` 或列出失败项 | 任何时候，自己跑 |
| GitHub 上的对勾 | 仓库 Actions 页面，每次提交旁边有 ✅ 或 ❌ | 每次推送自动跑（2026-11-20 启用）：三个系统 × 两个 Python 版本，加密钥和依赖扫描 |
| 验收报告 | `reports/acceptance.md`：按下面的功能编号逐条列出 通过 / 失败 | 每次运行检查脚本自动重新生成 |

检查脚本依次执行：`ruff check`、`ruff format --check`、`mypy src`、`pytest --cov=eia`，然后生成验收报告。

## 2. 功能 ↔ 测试对照表

每个功能有编号。每条验收标准对应至少一个自动测试，测试函数名里带编号（如 `test_F4_02_...`），所以报告能按功能汇总。

## 3. 测试数据

- `tests/fixtures/` 放**脱敏的**样例导出：结构来自真实导出，内容全部替换为虚构文字。
- 每个样例文件名带平台和采集日期（如 `chatgpt-2026-11.json`）。平台改了导出格式时，新增样例，旧样例保留。
- 真实对话永远不进代码仓库。M-04 用的真实数据只留在你本机。

## 4. 改代码时的规则

1. 新功能：先写失败的测试，再写代码让它通过。
2. 修 bug：先写一个能重现这个 bug 的测试，再修。这个测试永久保留。
3. 已有测试不许删除、跳过或放宽来让结果变绿。确实要改，在提交说明里写原因，并在这份文档的对照表里同步修改。
4. 新增功能必须先在对照表里加编号和验收标准，再开工。
5. 每个任务完成时，交付内容包括 `check.ps1` 的实际输出，不接受"应该没问题"。

## 5. 后续版本

V1、V2 的每份 spec 批准时，在本文件追加对应的功能编号段落（F8 起）。涉及 LLM 的测试一律用模拟返回，不花钱、不依赖网络；真实调用的测试单独标记，手动跑。
